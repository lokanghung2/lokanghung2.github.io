一、 明確定義兩大人類角色規範 (Roles & Responsibilities)

落實 Human-in-the-Loop 與以人為本，嚴格區隔「業務管理」與「知識語意」權責

Core Human Factors
角色 1 • 業務決策 最終決策與放行者

業務管理者 / 營運主管

Business Manager / Facility Director

適合人選：總務處長、廠務主管、ESG 永續經理、大樓物業營運總監。

核心職責：

  • 自然語言動口下目標：直接以業務目標溝通（「壓低夏季尖峰」、「依會議排程預冷兼顧電費」）。
  • 補齊業務情境資訊：空間無感測器時，回答 AI 主動探詢的預估人數與場地用途。
  • 策略審核與一鍵核准：檢視 AI 方案與預測曲線，點擊【一鍵核准】放行。
  • 商談介面需求與驗收樣板：表達日常監控偏好，體驗並驗收商談生成的「介面樣板」。

💡 操作邊界：純業務與效益視角，零技術門檻，完全不接觸程式碼、API 規格或配線。

角色 2 • 知識架構 空間建模與語意轉譯者

建築語意架構師

Building Knowledge Architect

適合人選：弱電/BMS 系統整合工程師 (SI)、BIM 建模師、機電物聯網架構師。

核心職責：

  • Block 空間畫布建模：在視覺畫布上拼裝 Block（堆疊、相連、內裝），定義幾何拓撲。
  • 全域 API 裝載與情境綁定：將 IoT API 拖入 Block，為外部 API/MCP 設定區域與業務情境。
  • 校準語意與邊界 (Semantic)：定義物理量、單位、保護邊界與外部 API 費用配額。
  • 打造與維護「介面樣板」：與主管商談對齊需求，發布標準樣板並批次套用到全棟標準層。

💡 操作邊界：專注於空間拓撲、Block 與全域 API 語意的精確性，不負責日常營運放行。

比較維度 角色 1：業務管理者 / 營運主管 角色 2：建築語意架構師
關注核心 節能效益、生產產量、電費成本、營運安全 空間拓撲、全域 API 對應、物理量語意、Block 完整性
系統輸入 自然語言目標、業務情境確認、一鍵核准指令 Block 空間建模、API/MCP 裝載綁定、介面樣板生成
操作介面 生成式決策卡片、效益滑桿、危機分診面板 Block 視覺化畫布、拖拉綁定抽屜、樣板配置器
參與時機 日常營運、隨時下達目標、審核高風險任務 系統初期建置、空間/設備異動、外部 API/MCP 接入

二、 系統總體定位與架構設計願景 (Vision & Design Principles)

融合多 Agent 協同、語意驅動與動態事件的自主閉環生態系

Everything as API

全部以 API 為基準

IoT 設備、外部氣象/電價服務與企業 MCP 服務完全平等對待，統一定義為 API + Semantic + Context，AI 面向統一能力庫流暢推理。

Two-Tier Context

雙層 Context 架構

API 層固化「結構情境（Structural Context）」供秒級檢索；Shell 層承載「運行情境（Runtime Context）」供決策守護，徹底消除冷啟動死結。

Universal Agent Shell

通用智能外殼與 Event

Agent Shell 按需掛載，將被動外部 API 轉化為主動動態 Event；完成協商後安全卸載，事件由輕量骨幹獨立守護。

五、 全部以 API 為基準（Everything as API）與雙層 Context 模型

統一能力描述公式：能力 = API + Semantic + Context

API 類型 來源範例 API (操作/查詢) Semantic (語意與限制) Structural Context (結構情境)
現場 IoT API VRV 空調、水泵、電表 set_temperature(23) 單位 °C、安全範圍 18~28、調溫滯後 5 分鐘 拓撲：冷卻水迴路 #2、服務對象：12F 辦公區、(按需)裝載於【1202 會議室 Block】
外部服務 API 氣象局、台電即時電價 get_current_tariff() 氣溫 °C、尖離峰電價 (NTD/kWh)、呼叫配額 區域：台北大安區、費率：經常契約夏季高壓時段、碳排：台電基準因子
外部 MCP 服務 Google Calendar、ERP list_room_bookings() 會議時間、進駐人數、VIP 等級說明 組織：產品研發處、會議室：12F 大會議室專用行事曆、業務：外賓接待流程

核心架構突破：Context 的「靜動分離（Two-Tier Context）」

若將 Context 只交給 Agent Shell，Task Agent 找設備時會遇到「冷啟動陷阱」（必須喚醒大樓 500 台冷氣的 Shell 挨個詢問），且 Shell 卸載時設備將失憶；反之若全寫死在 API 靜態定義中，則動態任務記憶無處安放。因此系統確立了清晰的雙層劃分：

第 1 層：結構情境 (Structural Context)

載體：固化於 IoT / 外部 API 資產目錄與圖譜。

本質：靜態客觀事實（設備迴路、服務區域、所屬系統、可選關聯 Block）。

使命：供 Task Agent 做秒級全域檢索與空間推理（零 AI 算力開銷）。

第 2 層：運行情境 (Runtime Context & Memory)

載體：動態載入於 Agent Shell 內部（存於 NATS KV 快取）。

本質：動態主觀記憶（當前 VIP 任務鎖定、設備運作延遲傾向、API 呼叫配額餘額）。

使命：供 Agent 做即時決策與智慧護航（任務結束後沉澱至日誌）。

六、 通用 Agent Shell 智能外殼機制

按需掛載、創造動態 Event、管理快取限流，並在任務完成後安全卸載

1. 動態事件創造者 (Event Emulation)

氣象局或行事曆本身是「被動」的。Shell 掛載後，讀取外部資料並在底層事件系統註冊「開會前 20 分鐘鬧鐘」或「紫外線危險級通知」，隨即卸載。把被動 API 轉化為主動 Event！

2. 限流、費用與快取專屬記憶

為外部商業 API 守門。記錄「氣象資料 30 分鐘才更新，3 分鐘前才抓過，直接命中快取」，並在 API 費用達預算 80% 時自動實施退避降頻保護。

3. MCP 工具自適應打量 (Introspection)

MCP Shell 連接外部 MCP Server，自動打量並自適應其 Tools 與 Prompts，將原生協定轉譯為系統標準 API + Semantic + Context 目錄。

七、 Block 空間基元（可有可無・按需啟用）

單一空間載體：可堆疊、可相連、可內裝，與 API 同級對等

內裝 (Nest / Contain)

支援無窮層級碎形包含：園區 Block ➔ 大樓 Block ➔ 12樓 Block ➔ 1202大會議室 Block。

堆疊 (Stack)

垂直空間堆疊：12 樓 Block 堆疊於 11 樓之上，輔助推算熱浮效應與管路垂直水壓。

相連 (Connect / Adjacent)

水平空間相鄰：1201 會議室與 1202 辦公室相連，輔助推算隔牆熱傳導與冷氣借冷擴散。

💡 解耦哲學：為什麼 Block 是「可有可無、按需啟用」？

流動感測器、氣象局天氣 API、測試工作台設備等，皆可完全脫離 Block，依靠自身 API + Semantic + Context 獨立自主運作！只有當系統需要地理拓撲空間推理（相鄰借冷、熱傳導）或需要驅動 AI 自動生成樓層平面圖/熱力圖/拖拉畫布時，才將 API 裝載於 Block！

按需生成哲學
